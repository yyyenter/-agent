# Agent 评估体系：eval 集思路与架构

## 一、设计思路

### 1.1 为什么需要评估体系？

传统测试方法的局限性：

| 传统方法 | 问题 | 评估体系的改进 |
|----------|------|----------------|
| 人工测试 | 成本高、难以复现、主观性强 | 自动化执行、客观量化 |
| 单次测试 | 无法追踪长期变化 | 持续评估、趋势分析 |
| 黑盒测试 | 无法分析内部协作 | 多维度指标、过程追踪 |
| 功能测试 | 只验证是否工作 | 性能、质量、效率全维度 |

### 1.2 评估体系的设计原则

```
┌─────────────────────────────────────────────────────────┐
│                    四维评估模型                         │
├─────────────────────────────────────────────────────────┤
│  1. 任务完成度  →  结果质量                             │
│  2. 智能体协作  →  过程效率                             │
│  3. 记忆系统    →  上下文理解                           │
│  4. 系统健康度  →  稳定性                               │
└─────────────────────────────────────────────────────────┘
```

**核心理念**：
- **量化优先**：所有指标必须可测量
- **分层设计**：从宏观到微观，层层递进
- **自动化**：支持持续集成/持续评估
- **可解释**：每个指标都有明确的业务含义

## 二、量化指标体系

### 2.1 任务完成度 (Task Completion)

衡量 Agent 最终输出是否满足用户需求。

| 指标 | 计算公式 | 满分 | 说明 |
|------|----------|------|------|
| **准确率 (Accuracy)** | 基于关键字匹配和语义理解 | 10 | 输出符合用户需求的程度 |
| **完整性 (Completeness)** | (已包含要素数 / 期望要素数) × 10 | 10 | 行程包含时间、地点、交通等要素的完整度 |
| **收敛性 (Convergence)** | 10 - max(0, 调整轮次 - 2) × 1.5 - 熔断惩罚 | 10 | 多少轮次完成（轮次越少越好） |
| **综合得分** | Accuracy×0.4 + Completeness×0.35 + Convergence×0.25 | 10 | 加权平均 |

**要素覆盖度检查清单**：
```python
EXPECTED_ELEMENTS = [
    "时间安排",  # 是否有"天"、"上午"、"下午"等时间标记
    "地点",      # 是否提及具体城市/景点
    "交通方式",  # 是否有"地铁"、"公交"、"打车"等交通信息
    "餐饮推荐",  # 是否有"吃饭"、"餐厅"、"早餐"等餐饮信息
    "预算",      # 是否提及"预算"、"花费"、"价格"
]
```

### 2.2 智能体协作 (Collaboration)

衡量 Planner → Execute → Validator 三个 Crew 的协作效率。

| 指标 | 数据来源 | 满分 | 说明 |
|------|----------|------|------|
| **路由正确率** | `intent_router` 输出 | 10 | Planner 决策是否合理（旅行 vs. 闲聊） |
| **工具调用有效性** | 工具调用日志 | 10 | WeatherTool、MemoryTool 的命中率 |
| **质检反馈质量** | Validator 输出 | 10 | 反馈是否有明确指导意义（通过/重做/继续） |

**协作流程追踪**：
```
用户消息
    ↓
[PlannerCrew] 决策 → is_complex? / simple_answer?
    ↓ 是
[TravelExpertCrew] 执行 → 生成 draft_report
    ↓
[ValidatorCrew] 质检 → feedback_type: pass/error/adjust/continue/ask_user
    ↓ 需要修正
[TravelExpertCrew] 执行 (修正) ← 循环
    ↓
最终报告
```

### 2.3 记忆系统 (Memory)

衡量四级记忆系统的有效性和准确性。

| 指标 | 计算方式 | 满分 |
|------|----------|------|
| **偏好提取准确率** | 匹配用户输入与提取结果 | 10 |
| **长期记忆利用率** | SaveMemoryTool 写入频次与价值 | 10 |
| **上下文一致性** | 检查是否记得历史对话 | 10 |

**记忆系统架构**：
```
┌─────────────────────────────────────────────────────────┐
│                   四级记忆存储                          │
├─────────────────────────────────────────────────────────┤
│  情节记忆 (桶3)   →  Redis List     → 原始对话轮次     │
│  工作记忆 (桶5)   →  Redis Hash     → 临时行程约束      │
│  工具缓存 (桶4)   →  Redis KV       → 全局工具缓存      │
│  语义记忆 (桶6)   →  SQLite         → 用户长期偏好      │
└─────────────────────────────────────────────────────────┘
```

### 2.4 系统健康度 (System Health)

衡量系统的响应速度和稳定性。

| 指标 | 计算方式 | 警戒线 |
|------|----------|--------|
| **响应延迟** | 从请求到完成的总耗时 | >30秒 |
| **错误率** | 异常/中断次数 / 总请求数 | >5% |
| **熔断触发率** | circuit_breaker_triggered / 总请求数 | >10% |

## 六、持续改进

### 6.1 定期评估周期

- **每日**：自动化回归测试
- **每周**：全面评估 + 质量分析
- **每月**：深度分析 + 优化建议

### 6.2 改进方向

1. **增加测试用例**：根据实际用户反馈补充边界 case
2. **调整权重**：根据业务重点调整各维度权重
3. **引入 LLM Judge**：使用 LLM 进行更智能的语义评估
